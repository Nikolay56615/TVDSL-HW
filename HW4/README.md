# HW4 — IR и базовые оптимизации Funny

Четвёртое домашнее задание по курсу [TVDSL](https://github.com/nsu-fit/TVDSL).
Проверенный AST из HW3 переводится в трёхадресный код с базовыми блоками.
Для обеих версий IR строятся CFG, живость, граф конфликтов и жадная раскраска.
Интерпретатор позволяет сравнивать результаты до и после оптимизаций.

## Установка и запуск

Нужен **Python 3.10+**, сторонних зависимостей нет. HW4 использует HW1–HW3
из этого же репозитория и готовую таблицу `HW1/generated/dfa.min.json`.
После скачивания или клонирования перейдите в каталог репозитория
и проверьте интерпретатор; если каталог называется иначе, замените имя:

```powershell
cd TVDSL-HW
python --version
```

Все команды ниже выполняются из корня репозитория. В Linux/macOS можно
заменить `python` на `python3`, в Windows — на `py`.

```powershell
python -m HW4.funnyir build HW4/examples/good_basic.funny
python -m HW4.funnyir build HW4/examples/good_basic.funny --format text
python -m HW4.funnyir build HW4/examples/good_basic.funny --format json --out ir.json
python -m HW4.funnyir build HW4/examples/good_loop.funny --cfg-dot cfg.dot --interference-dot conflicts.dot
python -m HW4.funnyir run HW4/examples/good_basic.funny --args '[7]'
python -m HW4.funnyir run HW4/examples/good_loop.funny --args '[10]' --compare
python -m HW4.funnyir run HW4/examples/good_arrays.funny --args '[[1,2,3]]'
python -m HW4.funnyir run HW4/examples/good_recursion.funny --args '[6]' --compare
python -m HW4.funnyir build HW4/examples/good_cse.funny --format text
python -m HW4.funnyir build HW4/examples/good_cse.funny --format text --no-cse
python -m HW4.funnyir run HW4/examples/good_cse.funny --args '[2,3]' --compare
python -m HW4.funnyir build --text 'main() returns r:int { r = 2 + 3; }'
python -m HW4.funnyir test
python -m HW4.funnyir test -v
python -m unittest discover -s HW4/tests
```

Обычный `build` выводит `Ошибок нет.` или сообщения об ошибках.
IR и метрики выводятся с `--format text`, полный JSON — с `--format json`.
Это же правило действует при сохранении через `--out`.

Обычный `run` печатает JSON-массив возвращаемых значений: для первого
примера это `[12]`, для массива — `[[9, 2, 3], 1]`. Внешний список всегда
соответствует объявленным возвратам, поэтому один возвращаемый массив
также находится внутри внешнего списка.

| Команда или флаг | Назначение |
| --- | --- |
| `build FILE` / `build --text SOURCE` | построить и проверить IR; вывести `Ошибок нет.` или ошибки |
| `--format text` | показать IR до/после и метрики |
| `--format json` | полный результат компиляции, включая анализ обеих версий |
| `--out PATH` | сохранить основной вывод в UTF-8 |
| `--no-opt` | отключить все оптимизации; `before` и `after` совпадут |
| `--no-constants` | отключить локальное распространение и свёртку констант |
| `--no-simplify` | отключить безопасные алгебраические упрощения |
| `--no-cse` | отключить локальное устранение общих подвыражений |
| `--no-dce` | отключить удаление мёртвых вычислений |
| `--table PATH` | выбрать JSON-таблицу ДКА HW1 |
| `--cfg-dot PATH` | сохранить CFG после оптимизации |
| `--interference-dot PATH` | сохранить граф конфликтов и цвета после оптимизации |
| `build --function NAME` | выбрать функцию для DOT; по умолчанию первая |
| `run --function NAME` | исполнить выбранную функцию; по умолчанию `main` |
| `run --args JSON` | список аргументов; по умолчанию `[]` |
| `run --before` | исполнить IR до оптимизаций |
| `run --compare` | исполнить обе версии и сравнить результаты/коды ошибок |
| `--max-steps N`, `--max-depth N` | лимиты исполнения: 100000 инструкций и 128 вызовов |
| `test --cases PATH` | использовать собственный набор эталонов |
| `test -v` | показать каждый исходник, аргументы, ожидаемый и фактический результат |

`run` поддерживает те же флаги оптимизаций, таблицы, сохранения и DOT.
`--before` и `--compare` взаимоисключающие. DOT — обычные текстовые файлы;
для их чтения Graphviz не требуется. При установленном Graphviz можно
построить картинку командой `dot -Tsvg cfg.dot -o cfg.svg`.

Коды завершения: **0** — успех или совпавшие наблюдения при `--compare`;
**1** — ошибки исходной программы, исполнения, несовпадение эталона либо
незавершённое сравнение; **2** — неправильный запуск, аргументы, файлы или
таблица ДКА. Некорректные JSON-аргументы и отсутствующая функция дают 2.
Обычный `run` при runtime-ошибке даёт 1; `--compare` с одинаковой обычной
ошибкой даёт 0, поскольку наблюдения совпали.

## Формат IR

IR состоит только из словарей, списков и скаляров JSON. Модуль имеет
`version=1`, список `functions` и список исходных типизированных `formulas`.
Функция содержит `name`, `params`, `returns`, `locals`, `types`, `entry`,
`blocks`, `contracts`. Объявления переменных записываются как
`{"name":"x","type":"int"}`. `types` отображает регистры в `int`, `int[]`
или внутренний `bool`.

Регистры исходных имён имеют вид `v:x`, временные — `t:0`, `t:1`, …
и нумеруются отдельно в каждой функции. Блок имеет `label`, например `B0`,
и список `instructions`; последняя инструкция — ровно один терминатор.
Каждая инструкция сохраняет `pos={"line":…, "col":…}` из исходника.
Операнд имеет ровно один вид: `{"const":5}` или `{"var":"v:x"}`.
Это отличает имя регистра от константы без разбора строк.

| `op` | Основные поля | Смысл |
| --- | --- | --- |
| `copy` | `dest`, `args:[value]` | скопировать значение |
| `unary` | `dest`, `operator`, `args:[value]` | `-`, `not` |
| `binary` | `dest`, `operator`, `args:[left,right]` | арифметика или сравнение |
| `call` | `dests`, `name`, `args` | вызов с одним/несколькими результатами |
| `length` | `dest`, `args:[array]` | длина массива |
| `get` | `dest`, `args:[array,index]` | чтение элемента |
| `set` | `dest`, `args:[array,index,value]` | создать обновлённую копию массива |
| `spec` | `kind`, `predicate`, `args:[]` | сохранённый `assert`/`assume` |
| `jump` | `target` | безусловный переход |
| `branch` | `args:[condition]`, `then`, `else` | условный переход |
| `return` | `args` | объявленные результаты в порядке сигнатуры |

У Funny нет исходного оператора `return`: его добавляет HW4 в конце функции.
`call` сначала получает все аргументы, затем одновременно определяет `dests`.
При `x,y = f(y,x)` правая часть вычисляется полностью до записей в `x,y`.
Каждое чтение имени и литерала сначала получает временный регистр: поэтому
не теряются порядок вычислений и место возможной ошибки.

`and`, `or`, `->` переводятся в ветви CFG с коротким вычислением;
`not` меняет местами цели. У `while` есть заголовок проверки, тело, выход
и обратное ребро. Функциональное обновление массива приходит из HW2
как `ArrayUpdate` и становится `set` с последующим `copy` в исходное имя.
Параметры остаются доступными только для чтения, как требует HW3.

`contracts` содержит типизированные AST для `requires`, `ensures` и
`invariants:[{"block":…, "predicate":…}]`. Формулы, кванторы и спецификации
сохраняются для дальнейшей верификации. Интерпретатор HW4 **не исполняет
и не доказывает** их; в частности, `assume false` не останавливает программу.

## Python API и данные анализа

```python
from HW4.funnyir import compile_source, compile_ast, execute, IRRuntimeError

result = compile_source('main(x:int) returns r:int { r = x + 0; }')
if result.ok:
    print(execute(result.after, 'main', [7]))  # [7]
    print(result.metrics)
else:
    print(result.to_dict()['diagnostics'])
```

`compile_source(source, *, optimize=True, constants=True, simplify=True,
cse=True, dce=True, table=None)` подключает предыдущие этапы. `compile_ast(ast, *,
optimize=True, constants=True, simplify=True, cse=True, dce=True)` повторно проверяет
копию дерева через HW3 и не меняет переданный AST. Оба возвращают
`CompilationResult` с `ok`, `before`, `after`, `diagnostics`,
`analysis_before`, `analysis_after`, `metrics`, `to_dict()`.
При ошибках HW1–HW3 оба IR равны `None`, исходная диагностика сохраняется.

`optimize_module(module, *, constants=True, simplify=True, cse=True, dce=True)`
из `HW4.funnyir.optimize` возвращает оптимизированную копию готового IR.

`analysis_before` и `analysis_after` отображают имя функции в результат
`analyze(function)`: `cfg`, `blocks`, `interference`, `colors`, `color_count`.
У каждого узла CFG есть `successors`, `predecessors`, `reachable`.
У каждого блока — `use`, `defs`, `live_in`, `live_out`. Граф конфликтов —
отображение регистра в отсортированный список соседей без петель;
`colors` отображает регистр в номер цвета с нуля.

`execute(module, function='main', arguments=None, *, max_steps=100000,
max_depth=128)` возвращает список результатов. `IRRuntimeError` содержит
`code`, `message`, `pos` и `to_dict()`. Основные коды:
`division_by_zero`, `array_bounds`, `uninitialized`, `step_limit`,
`recursion_limit`; API также проверяет число и типы входных аргументов.
Входные массивы Python не изменяются.

Исполнение и свёртка констант используют одинаковый знаковый **int32**
с переполнением по модулю 2³². Например, `2147483647+1 = -2147483648`.
Деление округляется к нулю: `-7/3 = -2`; `MIN_INT/-1 = MIN_INT`.
Литералы и входные целые также нормализуются до int32. `bool` не считается
целочисленным аргументом. Массивы имеют семантику копирования.

## Краткий отчёт: оптимизации и эффект

Реализованы локальное распространение констант, свёртка арифметики/сравнений,
тождества `x+0`, `0+x`, `x-0`, `x*1`, `1*x`, `x/1`, локальный CSE
и DCE на основе живости. Порядок: константы/упрощения → CSE → DCE.
Все проходы включены по умолчанию; `--no-cse` отключает только CSE,
`--no-opt` — все оптимизации. В Python API у CSE параметр `cse=True`.
Известные константы сбрасываются при записи и не переносятся между блоками.
Деление на ноль при свёртке остаётся инструкцией, чтобы ошибка возникала
во время исполнения на прежнем пути.

CSE заменяет повторную чистую операцию копией доступного прежнего результата.
Он сравнивает текущие значения операндов, учитывает копии и перезаписи,
забывает информацию на границе блока. Поддерживаются `+`, `-`, `*`, сравнения,
унарные `-` и `not`; для `+`, `*`, `==`, `!=` учитывается перестановка аргументов.
Деление, операции с массивами, вызовы и спецификации не заменяются CSE.
В `good_cse.funny` два исходных `a+b` становятся одним сложением и копией;
`main(2,3)` до и после возвращает `[10]`. Инструкций **13 → 11**, временных
**9 → 7**, цветов **4 → 2**; итоговое сложение `x+y` остаётся.

DCE повторяется до стабильности. Вызовы, `get`, `set`, `length`, деление,
спецификации и терминаторы сохраняются. Мёртвую чистую операцию можно убрать,
только если каждый её регистровый операнд определён на всех входящих путях.
Для этого отдельный анализ определённости берёт пересечение по предшественникам.
Иначе даже неиспользуемое `unused=x+1` могло бы потерять ошибку чтения `x`.
Правила `x*0`, `x/x`, `0/x` без дополнительных доказательств не применяются.

Живость считается до неподвижной точки, включая обратные рёбра циклов:
`OUT[B] = ⋃ IN[S]` по преемникам и
`IN[B] = USE[B] ∪ (OUT[B] − DEF[B])`. Конфликты строятся по инструкциям;
одновременно нужные входные значения также конфликтуют. Жадная раскраска
обходит вершины по убыванию степени, при равенстве — по имени. Участвуют
и исходные, и временные регистры. Это подготовка к распределению регистров,
а не окончательное назначение JVM-слотов или машинных регистров.

Для `good_basic.funny` число инструкций уменьшается **19 → 5**, используемых
временных **14 → 3**, цветов **4 → 1**; блок остаётся один.
При `main(7)` обе версии возвращают `[12]`.
Метрики считают терминаторы среди инструкций и только упомянутые временные,
поэтому сохранённые записи удалённых временных в `types` в счётчик не входят.
Число цветов модуля — максимум по функциям: их кадры могут переиспользовать
цвета. JSON содержит отдельные результаты анализа каждой функции.

## Тесты и сохранённые примеры

В `tests/cases.json` находятся **49 эталонов**: 31 успешное исполнение,
13 ожидаемых runtime-ошибок, включая 2 защитных лимита, и 5 некорректных
исходных программ. Каждый исполнимый случай проверяется по эталону отдельно
до и после оптимизаций. PASS у негативного случая означает ожидаемый отказ.
Проверено **150/150 unittest**: 36 проверок исполнения/API, 15 генерации IR,
22 анализа/базовых оптимизаций, 33 CSE и 44 CLI. Подпроверки внутри методов не увеличивают
это число.

Формат своего набора:

```json
{"cases":[
  {"name":"Сумма","input":"main(x:int) returns r:int {r=x+1;}","args":[2],"result":[3]},
  {"name":"Деление","input":"main() returns r:int {r=1/0;}","error":"division_by_zero"},
  {"name":"Имя","input":"main() returns r:int {r=unknown;}","valid":false,
   "diagnostics":[{"phase":"semantic","code":"unknown_variable"}]}
]}
```

`function` по умолчанию `main`, `args` — `[]`. В `diagnostics` можно задать
часть полей, но число и порядок сообщений должны совпасть. Поле `message`
проверяется как подстрока, остальные — точно. `max_steps` и `max_depth`
у случая задают собственные положительные лимиты.

В `examples/` есть 10 корректных программ, 2 программы с runtime-ошибками
и 2 некорректных исходника. `expected_results.json` задаёт их аргументы
и ожидаемые результаты. Для `good_basic` сохранены полный JSON,
текст до/после, результат сравнения и оба графа DOT:
`good_basic.output.json`, `good_basic.output.txt`, `good_basic.run.json`,
`good_basic.cfg.dot`, `good_basic.interference.dot`.
Для CSE сохранены `good_cse.output.json`, `good_cse.output.txt`
и `good_cse.run.json`.
Проверки CLI сверяют сохранённые результаты с текущей реализацией.

`--compare` проверяет наблюдения **на одном заданном входе**, включая типы
значений и коды ошибок. Это не доказательство эквивалентности на всех входах.
При `step_limit`/`recursion_limit` выводится `equivalent:null`,
`comparison:"inconclusive"` и код 1, даже если оба лимита одинаковы.
В эталонных тестах ожидаемый лимит может дать PASS как проверка защиты;
в подробном выводе отдельно сказано, что эквивалентность не установлена.

Ограничения: SSA/phi, межблочный CSE и распространение констант, удаление
недостижимых блоков, spilling и генерация байт-кода не реализованы.
Контракты не доказываются, завершение не устанавливается, глубина обхода
очень большого AST зависит от стека Python. Подмножество исходного языка
совпадает с HW3: нет строк, массивных литералов, объявляемых `bool` и `int[][]`.
